# 일일 리포트 작성

## 흐름

1. `summarize_daily_logs`로 리포트 날짜를 집계한다. 숫자와 목록은 모두 이 결과가 기준이다.
2. 아래 "판단할 것" 세 가지를 한 번에 판단한다.
3. 코드가 판단 결과를 HTML 리포트에 넣고 `publish_report`로 발행한다.

서버 러너에서는 1과 3을 코드가 하고, 모델은 2만 한다.

## 판단할 것

입력은 JSON이다. `facts`는 집계 숫자, `pattern_table`은 오류 메시지 패턴표, `unmatched_messages`는 패턴표와 정확히 일치하지 않는 메시지, `cluster_candidates`는 코드가 조건(같은 신호, 같은 속성, 2시간 안, 3대 이상)으로 추린 묶음 후보다.

### 1. 처음 보는 오류 메시지 분류

메시지마다 패턴표의 `message_pattern` 중 같은 원인을 가리키는 것을 고르고, 어느 것에도 해당하지 않으면 `NEW`를 고른다. 대소문자, 앞뒤 접두어(`java.lang.` 등), 단어 순서, 단위 표기가 달라도 원인이 같으면 같은 패턴이다. 원인이 다르면 겉보기 단어가 겹쳐도 `NEW`다. 예를 들어 인증서 만료나 디스크 부족은 패턴표의 어느 원인과도 같지 않다. `reason`에는 판단 근거를 한 문장으로 쓴다.

### 2. 공통 원인 묶음 판단

후보마다 같은 원인으로 함께 생긴 이상인지 판단한다. `meaningful`은 다음일 때만 true다.

- PC들의 오류 메시지가 같은 원인을 가리킨다(같은 패턴). 이상 유형이 "error"로 같다는 것만으로는 부족하다. 메시지가 서로 다른 원인이면 우연히 모인 것이다.
- 공유 속성이 그 원인을 설명한다. 예: 같은 클라이언트 버전에서 같은 라이선스 오류, 같은 사내망 IP(같은 프록시)를 쓰는 PC들의 동시 접속 거부와 신호 끊김.
- 여러 후보가 같은 사건을 다른 각도로 잡은 것이면, 원인을 가장 잘 설명하는 후보 하나만 true로 하고 나머지는 false로 한다.
- 원인이 PC 안에 있는 오류(포트 충돌 `bind failed`, 메모리 부족 `OutOfMemoryError`)는 같은 패턴이 여러 대에서 나도, 공유 속성이 그 원인을 직접 설명할 때만 true다. 같은 공정이나 같은 버전이라는 것만으로는 설명이 되지 않는다.

예시:
- 같은 사내망 IP 그룹 4대가 30분 안에 `heartbeat send failed` → true. 같은 네트워크 경로(프록시)를 공유한다는 것이 통신 지연을 설명한다.
- 같은 공정 3대가 2시간 안에 `bind failed` → false. 포트를 다른 프로세스가 쓰는 것은 PC마다의 문제이고, 공정이 같다는 것은 이를 설명하지 않는다.
- 같은 버전 4대가 1시간 안에 같은 키의 `config parse failed` → true. 그 버전의 배포 설정이 원인으로 설명된다.

`cause`에는 추정 원인을 한 문장으로 쓴다. false이면 왜 우연으로 보는지 쓴다.

`proxy_pc`는 프록시 장애로 판단한 묶음에만 PC ID 하나를 쓰고, 그 밖에는 빈 문자열로 둔다. 프록시 PC는 같은 사내망 IP 그룹(`shared_intranet_ip`)에 속하면서 같은 시간대에 신호만 끊기고 오류가 없는 PC다. 사내망 IP 그룹이 다른 PC는 같은 시간대에 끊겼더라도 프록시 PC가 아니다.

### 3. 요약 문장

운영자가 아침에 30초 안에 읽을 수 있게 3~5문장으로 쓴다. 정상 PC 비율, 이상 PC 수와 전일 대비, 의미 있는 묶음, 식별 실패와 확인 필요를 우선순위대로 다룬다.

- 숫자는 `facts`에 있는 값만 그대로 쓴다. 계산하거나 세어서 새 숫자를 만들지 않는다(차이, 비율, 합계, 대수 포함). 묶음의 PC 수는 `facts.cluster_candidate_pc_counts`의 값을 쓴다.
- 오류 메시지 속 숫자(포트, 시간, 줄 번호)와 시각은 요약에 쓰지 않는다. 오류는 패턴 이름으로 부른다.
- PC ID는 묶음이나 식별 실패를 설명할 때만 쓴다.
- 입력에 없는 사실을 추측해서 쓰지 않는다.
