# 설정 수정과 서비스 재시작은 사람 승인 없이 자동 실행한다

문의 대응의 대상은 이미 실행되지 않는 클라이언트라서 재시작 자체의 위험은 낮다. 실제 위험은 잘못된 PC를 대상으로 지정하는 것과 잘못된 값을 쓰는 것이다. 그래서 승인 절차 대신, 기준정보에 있는 PC이고 정지 상태일 때만 조치하고, 쓰는 값은 모델이 아니라 코드가 정하며, 수정 전 백업과 재시작 후 검증과 실패 시 원복을 안전장치로 쓴다.

자동 조치는 세 가지다.

- 설정 키를 기본값으로 복구하고 재시작(config parse failed).
- 설정 수정 없이 재시작(connection refused, heartbeat send failed, license check timeout). 재시작은 위험이 낮으므로 일시적 원인일 가능성이 있으면 1회 시도한다.
- JVM 프록시 인자를 교정하고 재시작(프록시를 거치는 PC의 connection refused). 값은 ADR 0004로 정한다.

OOM과 bind failed는 재시작해도 다시 실패하므로 자동 조치하지 않는다. 조건 밖이면 실행하지 않고 운영자 확인으로 넘긴다. 조치 대상 PC는 모델이 아니라 코드가 문의의 설비 PC ID 필드(범위, 쉼표 목록)를 풀어 정하고, 한 문의에서 자동 조치하는 대수는 20대로 제한한다. 상한을 넘으면 앞에서부터 20대까지만 조치하고 나머지는 회신에 안내한다. PC마다 독립적으로 처리해, 한 대가 실패하면 그 PC만 원복한다.

## Considered Options

- **모든 수정에 사람 승인**: 건당 30분 → 5분이라는 목표를 달성하기 어렵다. 기각.
- **패턴표에서 고칠 수 있는 오류(config)만 자동 조치**: 일시적 원인으로 멈춘 클라이언트도 운영자에게 넘어가 목표 시간을 지키기 어렵다. 재시작의 위험이 낮다는 판단과도 맞지 않는다. 기각.

## Consequences

- 개선 과정 기록에 "잘못된 PC 대상 실행 건수", "재시작 후 복구 성공률"을 숫자로 적는다.
- 수정 없이 재시작만 했다가 실패한 PC는 원복할 것이 없으므로 "재시작 실패"로 기록하고 권장 조치를 회신에 적는다.
