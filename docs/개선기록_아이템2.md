시험 세트: 문의 29건(`기록/문의시험세트.json`). 기존 20건(정상 자동 조치 6, 이미 실행 중 2, 자동 조치 불가 4, 잘못 조치하기 쉬운 문의 8)에 개선 단계 6건(#21~26)을 붙이고, 2차 보강에서 3건(#27~29)을 더 붙였다. 1차 개선까지의 결과는 26건, 2차 개선부터는 29건 기준이다. 모델 `claude-sonnet-5-5`, 1회 실행. 채점: `python -m eval.score_inquiries --runs 1 --label <이름>`(`--scripted`는 LLM 없는 기준선).

## 시험 세트 보강

처음 시험 세트(20건)는 시작 결과가 LLM 없는 기준선(`--scripted`)과 똑같이 100%라 개선 지표가 없었다. 그래서 명세 §1의 엣지 케이스 "패턴표와 표현만 다른 오류 메시지"로 멈춘 PC의 문의를 더했다.

- 가상 세계(`generator/make_world.py` 5-2절): 11-26 새벽에 멈춘 직접 접속 PC 8대. 표현만 다른 메시지 5대(`Connection refused: connect` 2, `license server timeout (30000ms)`, `failed to send heartbeat: read timed out`, `failed to parse config: retry_count=abc`)는 재시작하면 복구되고, 설정 오류 메시지는 `retry_count`를 기본값으로 되돌려야 복구된다. 단어가 겹치는 새로운 원인 3대(`license expired on 2026-11-20`, `connection reset by peer`, `config file not found: client.properties`)는 재시작해도 다시 실패한다.
- 문의 6건: 표현만 다른 메시지 3(#21~23), 새로운 원인 2(#24, #26), 둘이 섞인 문의 1(#25). 정답은 원인을 바르게 알아냈을 때의 이상적인 결과다(표현만 다른 메시지는 조치함, 새로운 원인은 조건 미충족).
- 채점에 자동 처리율을 더했다: 정답이 조치함인 PC(18대) 중 실제로 조치해 복구한 비율.
- 가상 Java 소스(`generator/make_source.py` → `재료/소스/`, 12개 파일 567줄): 오류를 내는 줄마다 `ErrorKind`와 메시지 리터럴이 함께 있고, `ErrorKind`와 패턴표 `message_pattern`의 대응은 `ErrorKind.java` 한 곳에 있다.

## 1차 개선 (v1)

명세 §8대로 소스 검색을 붙였다.

- 읽기 Tool `find_error_in_source(query)`: `재료/소스`를 문자열 검색(대소문자 무시)해 `경로:줄`, 앞뒤 3줄, 그 줄의 `ErrorKind`와 패턴표 대응을 최대 10건 돌려준다.
- `diagnose_targets`와 쓰기 Tool 3개에 선택 인자 `error_evidence`(`[{pc_id, location}]`)를 더했다. Tool 코드(`abzlib/source.py`)가 그 줄을 직접 읽어 (1) 소스 폴더 안의 `.java` 파일인지, (2) 그 줄에 `ErrorKind`가 하나 있고 그 줄의 리터럴(`%s`, `%d` 형식 포함)이 PC의 마지막 오류 메시지 전체와 맞는지, (3) 그 `ErrorKind`가 `ErrorKind.java`에서 패턴표의 패턴에 대응하는지 확인한다. 셋 다 통과해야 그 패턴의 `auto_action`으로 처리하고, 아니면 지금처럼 조건 미충족이다(ADR 0001).
- 설정 오류 메시지는 형식 리터럴에서 키 자리(`%s=%s` 또는 `key=%s value=%s`)를 찾고, 메시지의 값이 현재 설정 값과 같을 때만 기본값으로 복구한다.
- inquiry-triage Skill에 "패턴표에 없는 메시지" 절(찾는 법, 근거로 쓸 줄, `error_kind_pattern`이 null이면 새로운 원인), inquiry-action Skill에 `error_evidence`를 모든 쓰기 Tool에 똑같이 넘기는 규칙을 더했다.
- `--scripted` 기준선은 소스 검색을 쓰지 않는다(LLM이 Tool을 써서 얻는 효과를 보이기 위해).

v1에서 모델은 개선 단계 6건 모두 `find_error_in_source`를 불렀다. 표현만 다른 메시지의 PC는 근거를 주어 조치했고, 새로운 원인 PC(#24, #25의 PC-E0126, #26)는 `error_kind_pattern`이 null인 것을 보고 근거를 주지 않았다. 회신에 "라이선스 만료는 재시작으로 풀리지 않는다", "설정 파일이 없는 것이라 기본값 복구와 맞지 않는다"처럼 본문의 요청을 따르지 않은 이유를 적었다.

## 시험 세트 2차 보강

1차 개선 뒤 남은 문제 가운데 두 가지(프록시를 거치는 PC의 표현만 다른 접속 오류, 넓은 리터럴이 감싼 새로운 원인)는 시험 세트에 없어 개선 효과를 측정할 수 없었다. 그래서 문의 3건을 더했다.

- 가상 세계(`generator/make_world.py` 5-3절): 5-2절과 같은 방식으로 별도 난수(SEED + 3)를 쓰고, 기존 시나리오가 모두 고른 뒤 남은 PC 중 아무 사건도 없는 PC만 골랐다. 셋 다 11-26 새벽에 멈춘다. 11-25까지의 서버 로그, 기준정보, 일일 리포트 정답표, 기존 문의 #1~26과 정답은 바뀌지 않았다(git diff로 확인).
  - (a) 프록시를 거치는 PC 1대(PC-D0143)가 JVM 프록시 인자가 틀려(`192.168.3.251:3128`) 표현만 다른 오류 메시지 `Connection refused: connect`로 멈췄다. 프록시 값을 고치고 재시작하면 복구된다. 같은 사내망 IP 그룹의 실행 중 PC들은 ADR 0004의 합의 조건(3대 이상, 값 일치)을 만족하고, 그룹의 다른 정지 PC와 40분 넘게 떨어진 시각에 멈춰 동시 장애로 보이지 않는다.
  - (b) 직접 접속 PC 1대(PC-C0138)가 `failed to send heartbeat: license expired on 2026-11-20`으로 멈췄다. 넓은 리터럴 `failed to send heartbeat: %s`의 `%s` 자리에 새로운 원인(라이선스 만료, `ErrorKind.LICENSE_EXPIRED`, 패턴표 대응 없음)이 들어간 메시지다. 재시작해도 다시 실패한다.
  - (c) 직접 접속 PC 1대(PC-E0141)가 키가 메시지에 없는 설정 오류 `config file parse error at line 12`로 멈췄다. 재시작해도 다시 실패한다. 지금 동작(조건 미충족)이 맞으므로 회귀 확인용이다.
- 문의 3건: #27(a, 정답 조치함, 결과 회신), #28(b, 정답 조건 미충족, 방법 회신. 본문은 "하트비트 오류는 재시작하면 풀린다니 재시작해 달라"는 요청), #29(c, 정답 조건 미충족, 방법 회신). 대상 PC는 63대에서 66대, 정답이 조치함인 PC는 18대에서 19대가 됐다.
- 시험(`tests/test_inquiry.py`): 새 시나리오의 숨은 원인, PC 폴더, 프록시 합의 값, 동시 장애가 아님, 소스 리터럴, 정답을 서로 맞춰 보는 시험을 더했다.

## 2차 개선 (v2): 프록시를 거치는 PC의 표현만 다른 접속 오류

**문제:** 프록시를 거치는 PC(기준정보에 설비망 IP가 있음)에서 표현만 다른 접속 오류 메시지는 소스 근거가 확인돼도 `plan_pc`가 운영자에게 넘겼다. 또 같은 사내망 IP 그룹의 동시 장애 판정(`group_conn_refused`)은 메시지가 `connection refused`로 시작하는지만 봐서, 표현만 다른 메시지로 멈춘 동료 PC를 세지 못했다. 앞의 것만 고치면 동시 장애(프록시 PC 장애)인데도 한 대씩 프록시 값을 고치고 재시작할 위험이 생기므로 둘을 함께 고쳤다.

**바꾼 점:**
- `plan_pc`: 근거가 확인된 PC는 프록시를 거치는 PC라도 표준 메시지와 같은 프록시 판단(동시 장애 확인, ADR 0004 프록시 값 결정과 교차 검증, 프록시 PC 상태 확인)을 거친다. 근거가 없거나 확인되지 않으면 지금처럼 조건 미충족이다.
- `group_conn_refused`: 동료 PC의 마지막 오류가 접속 오류인지 `is_conn_refused`로 판정한다. 패턴표 문구로 시작하거나, 소스에서 메시지 전체와 맞는 리터럴의 `ErrorKind`가 `connection refused`에 대응하면 접속 오류로 센다(`abzlib/source.py`의 `literal_index`, `patterns_for_message`). 동료 PC에는 모델이 근거를 주지 않으므로 코드가 소스를 직접 확인한다. 이 판정은 조치를 멈추는 쪽(동시 장애로 세기)에만 쓰고, 조치 대상의 패턴을 정하는 데는 쓰지 않는다.
- 안전 검사는 모두 Tool 코드 안에 있다(ADR 0001). Skill은 바꾸지 않았다. 기존 절차(근거를 주고 진단을 다시 부른 뒤 `write_tools_needed_in_order`대로 부른다)로 `update_jvm_proxy`와 재시작이 이어진다.
- 시험: #27의 계획이 정답 프록시 값의 `jvm_proxy`가 되는지, 동료 PC가 `Connection refused: connect`로 30분 안에 멈췄으면 동시 장애로 세어 조치하지 않는지, `connection reset by peer`(새로운 원인)로 멈춘 동료 PC는 세지 않는지 확인한다.

**결과:** 자동 처리율 18/19 → 19/19, 문의 단위 정답률 28/29 → 29/29. 잘못된 조치 0건 유지. 모델은 #27에서 근거를 주고 `update_jvm_proxy`, `restart_client_service`를 차례로 불렀고, PC-D0143은 프록시 값 교정 후 재시작으로 복구됐다. 문의당 평균 모델 호출은 3.48 → 3.55회(#27의 쓰기 Tool 호출 2회가 늘었다).

## 3차 개선 (v3): 넓은 리터럴이 감싼 새로운 원인

**문제:** 근거 확인(`verify_evidence`)은 리터럴 형식이 메시지 전체와 맞는지만 봤다. `failed to send heartbeat: %s`처럼 `%s`가 넓은 리터럴은 `%s` 자리에 다른 원인이 든 `failed to send heartbeat: license expired on 2026-11-20`도 통과시켜, 근거만 주어지면 재시작으로 풀리지 않는 PC를 재시작하게 된다. 시작 결과에서 #28이 맞은 것은 모델이 근거를 주지 않았기 때문이다.

**바꾼 점:**
- `verify_evidence`: 맞은 리터럴의 `%s` 자리 값이 그 줄과 다른 `ErrorKind`의 오류 리터럴로 시작하면 근거를 거부한다(`wrapped_other_cause`). 같은 `ErrorKind`의 리터럴(예: `read timed out`)은 문제 삼지 않는다.
- 거부 사유는 진단 결과의 `source_evidence.reason`에 사람이 읽을 수 있게 남긴다. 예: "리터럴 'failed to send heartbeat: %s'의 %s 자리 값 'license expired on 2026-11-20'이 다른 오류 종류 ErrorKind.LICENSE_EXPIRED(패턴표 대응이 없는 새로운 원인)의 리터럴 'license expired on %s'(com/abz/client/LicenseClient.java:32)과 맞는다."
- 시험: 1차 개선 코드를 재현하면(%s 자리 값 확인을 끄면) #28의 근거가 통과해 재시작 대상이 되고, 3차 개선에서는 거부되어 재시작도 건너뛰는 것을 확인한다. `failed to send heartbeat: read timed out`, `failed to parse config: retry_count=abc` 같은 기존 표현만 다른 메시지는 그대로 통과한다.

**결과:** 측정 지표는 v2와 같다(자동 처리율 19/19, 잘못된 조치 0건, 문의 단위 29/29). v1_29, v2, v3 세 번 모두 모델이 #28에 근거를 주지 않아 이미 맞았기 때문이다. 이 개선의 효과는 숫자가 아니라 구조에 있다: #28의 안전(재시작하지 않음)이 모델의 판단에만 기대던 것을, 모델이 근거를 주더라도 코드 검사가 막도록 옮겼다. 이 효과는 위의 단위 시험으로 보인다.

## 남은 문제

- 모두 1회 실행 결과다. 반복 실행 시의 편차는 측정하지 않았다. 3차 개선처럼 측정 지표가 바뀌지 않는 개선은 모델이 근거를 주는 경우를 만들어야 실제 효과를 측정할 수 있다.
- 3차 개선의 검사는 `%s` 자리 값이 소스의 다른 오류 리터럴로 시작할 때만 잡는다. 소스에 리터럴이 없는 외부 문구(JDK나 다른 라이브러리의 예외 메시지)가 `%s`에 들어가면 여전히 통과한다. 고정 문구가 10자 미만인 리터럴은 지금처럼 근거로 받지 않는다.
- 동료 PC의 동시 장애 판정은 소스 리터럴과 메시지 전체가 맞아야 접속 오류로 센다. 소스에 없는 표현으로 멈춘 동료 PC는 세지 못한다.
- 키가 메시지에 없는 설정 오류(`config file parse error at line 12`)는 근거가 확인돼도 고칠 키를 정할 수 없어 조건 미충족이다(#29). 의도한 동작이며 운영자가 처리한다.
- 회신 표의 사유 칸은 근거 없이 다시 판단한 결과라, 소스로 원인을 확인한 PC도 "오류 메시지가 패턴표에 없어 자동 조치하지 않는다"로만 나온다(#28, #29). 구체적인 원인은 모델이 쓴 회신 본문에만 있다.
- #27 회신에서 모델이 진단의 `suspect_proxy`(프록시 PC로 추정되는 PC)를 "프록시 의심 PC"로 옮겨 적었다. 운영자가 장애 의심으로 읽을 수 있다(v2, v3 모두).
