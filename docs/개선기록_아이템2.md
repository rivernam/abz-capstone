# 아이템 ② 개선 기록

시험 세트: 문의 26건(`기록/문의시험세트.json`). 기존 20건(정상 자동 조치 6, 이미 실행 중 2, 자동 조치 불가 4, 함정 8)에 개선 단계 6건(#21~26)을 붙였다. 모델 `claude-sonnet-5-5`, 1회 실행. 채점: `python -m eval.score_inquiries --runs 1 --label <이름>`(`--scripted`는 LLM 없는 기준선).

## 시험 세트 보강

처음 시험 세트(20건)는 시작 결과가 LLM 없는 기준선(`--scripted`)과 똑같이 100%라 개선 지표가 없었다. 그래서 명세 §1의 함정 "패턴표와 표기만 다른 오류 메시지"로 멈춘 PC의 문의를 더했다.

- 가상 세계(`generator/make_world.py` 5-2절): 11-26 새벽에 멈춘 직접 접속 PC 8대. 표기 변형 5대(`Connection refused: connect` 2, `license server timeout (30000ms)`, `failed to send heartbeat: read timed out`, `failed to parse config: retry_count=abc`)는 재시작하면 복구되고, config 변형은 `retry_count`를 기본값으로 되돌려야 복구된다. 단어가 겹치는 신규 원인 3대(`license expired on 2026-11-20`, `connection reset by peer`, `config file not found: client.properties`)는 재시작해도 다시 실패한다.
- 문의 6건: 표기 변형 3(#21~23), 신규 원인 2(#24, #26), 변형과 신규가 섞인 문의 1(#25). 정답은 원인을 바르게 알아냈을 때의 이상적인 결과다(표기 변형은 조치함, 신규 원인은 조건 미충족).
- 채점에 자동 처리율을 더했다: 정답이 조치함인 PC(18대) 중 실제로 조치해 복구한 비율.
- 가상 Java 소스(`generator/make_source.py` → `재료/소스/`, 12개 파일 567줄): 오류를 내는 줄마다 `ErrorKind`와 메시지 리터럴이 함께 있고, `ErrorKind`와 패턴표 `message_pattern`의 대응은 `ErrorKind.java` 한 곳에 있다.

## 1차 개선 (v1)

명세 §8대로 소스 검색을 붙였다.

- 읽기 Tool `find_error_in_source(query)`: `재료/소스`를 문자열 검색(대소문자 무시)해 `경로:줄`, 앞뒤 3줄, 그 줄의 `ErrorKind`와 패턴표 대응을 최대 10건 돌려준다.
- `diagnose_targets`와 쓰기 Tool 3개에 선택 인자 `error_evidence`(`[{pc_id, location}]`)를 더했다. Tool 코드(`abzlib/source.py`)가 그 줄을 직접 읽어 (1) 소스 폴더 안의 `.java` 파일인지, (2) 그 줄에 `ErrorKind`가 하나 있고 그 줄의 리터럴(`%s`, `%d` 형식 포함)이 PC의 마지막 오류 메시지 전체와 맞는지, (3) 그 `ErrorKind`가 `ErrorKind.java`에서 패턴표의 패턴에 대응하는지 확인한다. 셋 다 통과해야 그 패턴의 `auto_action`으로 처리하고, 아니면 지금처럼 조건 미충족이다(ADR 0001).
- 설정 변형은 형식 리터럴에서 키 자리(`%s=%s` 또는 `key=%s value=%s`)를 찾고, 메시지의 값이 현재 설정 값과 같을 때만 기본값으로 복구한다.
- inquiry-triage Skill에 "패턴표에 없는 메시지" 절(찾는 법, 근거로 쓸 줄, `error_kind_pattern`이 null이면 신규 원인), inquiry-action Skill에 `error_evidence`를 모든 쓰기 Tool에 똑같이 넘기는 규칙을 더했다.
- `--scripted` 기준선은 소스 검색을 쓰지 않는다(LLM이 Tool을 써서 얻는 효과를 보이기 위해).

v1에서 모델은 개선 단계 6건 모두 `find_error_in_source`를 불렀다. 표기 변형 PC는 근거를 주어 조치했고, 신규 원인 PC(#24, #25의 PC-E0126, #26)는 `error_kind_pattern`이 null인 것을 보고 근거를 주지 않았다. 회신에 "라이선스 만료는 재시작으로 풀리지 않는다", "설정 파일이 없는 것이라 기본값 복구와 맞지 않는다"처럼 본문의 요청을 따르지 않은 이유를 적었다.

## 남은 문제

- 1회 실행 결과다. 반복 실행에서의 흔들림은 재지 않았다.
- 프록시를 거치는 PC의 표기 변형 접속 오류는 근거가 확인돼도 운영자에게 넘긴다(프록시 판단 규칙이 표준 메시지를 전제로 한다). 이 경우는 시험 세트에 없다.
- 키가 메시지에 없는 설정 변형(`config file parse error at line 12`)은 근거가 확인돼도 고칠 키를 정할 수 없어 조건 미충족이다.
- 소스 근거는 메시지 전체가 리터럴 형식과 맞는지만 본다. `%s`가 넓게 맞는 리터럴(예: `failed to send heartbeat: %s`)은 같은 앞부분의 다른 원인도 맞출 수 있다. 고정 문구가 10자 미만인 리터럴은 근거로 받지 않는다.
