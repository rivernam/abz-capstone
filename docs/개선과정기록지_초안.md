## 장 1. 아이템 ①

**아이템 이름:** 설비 PC 클라이언트 일일 상태 리포트 자동 생성

### 시작

**확인 방법:**
리포트는 매일 서버 로그를 집계해 이상 PC를 보여 준다. 이때 LLM이 판단하는 일은 세 가지다.
- 처음 보는 오류 메시지가 오류 패턴표(알려진 오류 목록)의 어느 항목에 해당하는지 분류한다.
- 공통 원인 후보가 실제로 같은 원인 때문인지 판정한다. 공통 원인 후보는 코드가 미리 추린 PC 목록이다. 같은 속성(공정, 설비 모델, 클라이언트 버전, 프록시)을 가진 PC 3대 이상이 2시간 안에 같은 종류의 이상을 보이면 후보 하나로 묶는다. 코드는 조건만 보고 묶으므로, 우연히 조건에 맞은 후보도 섞여 있다.
- 원인이 프록시 PC(여러 설비 PC의 통신을 중계하는 PC)라면 어느 PC인지 지목한다.

가상 서버 로그로 2026-11-21~25 닷새치 리포트를 만들어 정답 데이터와 비교한다. 날짜마다 LLM이 틀리기 쉬운 상황을 하나씩 넣었다.

| 날짜 | 넣은 상황 | 올바른 판정 |
|---|---|---|
| 11-21 | 패턴표와 표현만 다른 오류 메시지(예: `connection refused` 대신 `Connection refused: connect`) | 패턴표의 같은 항목으로 분류 |
| 11-22 | 같은 프록시를 쓰는 PC들의 동시 통신 장애. 같은 날 같은 공정의 PC 3대에 포트 충돌 오류가 따로따로 발생 | 앞의 것은 공통 원인, 뒤의 것은 공통 원인 아님 |
| 11-23 | 프록시 PC 장애로 그 프록시를 쓰는 PC들이 함께 끊김. 같은 공정이지만 그 프록시를 쓰지 않는 PC 1대도 같은 시간대에 따로 끊김 | 원인 프록시 PC를 지목하고, 따로 끊긴 PC는 원인에서 제외 |
| 11-24 | 특정 클라이언트 버전의 PC들에서만 같은 설정 오류 발생 | 버전 배포 문제로 공통 원인 |
| 11-25 | 같은 버전 PC들의 라이선스 확인 지연, 프록시 PC 장애, 같은 공정 PC 3대의 서로 다른 오류(메모리 부족, 포트 충돌, 통신 장애)가 하루에 섞임 | 앞의 둘은 공통 원인(프록시 PC 지목 포함), 마지막은 공통 원인 아님 |

1회 실행은 5일치 리포트 생성이다. 같은 입력으로 claude-haiku-5-5를 3회 실행했다.

규칙 기반 코드가 정하는 결과(이상 PC 검출 정밀도·재현율, PC 식별 실패 원인 분류)는 LLM과 무관하므로 따로 본다. LLM이 맡는 판단은 다음 지표로 평가한다.
- 오류 메시지 분류 정확도
- 공통 원인 탐지율: 진짜 공통 원인인 후보를 공통 원인으로 판정한 비율
- 공통 원인 오탐: 원인이 서로 다른 PC들을 공통 원인으로 잘못 판정한 횟수
- 프록시 PC 지목 정확도
- 출처 없는 숫자: 요약 문장의 숫자 중 입력 데이터에 없는 것. 모델이 직접 세거나 지어낸 숫자다.

**시작 결과:** 3회 실행 결과다. 1회 실행마다 5일치에 들어 있는 정답 개수를 분모로 적었다.
- 이상 PC 검출(코드): 3회 모두 5일 내내 정답과 일치했다. 놓친 PC 0대, 잘못 잡은 PC 0대.
- 오류 메시지 분류: 3회 모두 12/12
- 공통 원인 탐지: 3회 모두 5/5
- 프록시 PC 지목: 3회 모두 2/2
- 공통 원인 오탐: 우연히 조건에 맞은 후보가 1회 실행에 2개 있다. 3회 동안 모두 6번 판정했고, 그중 1번을 공통 원인으로 잘못 판정했다.
- 출처 없는 숫자: 3회 실행에서 총 8개(2개, 4개, 2개)

### 개선 1

**현재 문제:** 요약 문장에 입력 데이터에 없는 숫자가 3회 실행에서 총 8개 나왔다. 원인은 두 가지다.
- 공통 원인 후보에 속한 PC 대수를 모델이 입력의 PC 목록에서 직접 세어 "4대"로 썼다. 값은 맞았지만, 숫자는 코드가 계산한다는 설계 원칙에 어긋나고 틀릴 위험이 있다.
- 오류 메시지 안의 포트 번호(8443)를 요약에 그대로 옮겼다.

**고칠 계획:** 후보별 PC 대수를 코드가 계산해 입력에 넣는다. 프롬프트에 "직접 세지 말고 이 값을 쓴다", "오류 메시지 안의 숫자는 쓰지 않는다"를 명시하면 출처 없는 숫자가 0이 될 것이다.

**바꾼 점:**
- LLM 입력에 후보별 PC 대수 필드(`cluster_candidate_pc_counts`, `pc_count`)를 추가했다.
- 프롬프트(Skill 파일)에 숫자 사용 규칙 2줄을 추가했다.

**결과:**
- 출처 없는 숫자: 총 8개 → 0개
- 공통 원인 오탐: 6번 중 1번 → 6번 중 2번. 이번 변경과 관계없는 항목이다. 두 측정 모두 같은 후보(11-22 포트 충돌 3대)를 오판했으므로 LLM 출력의 실행 간 편차로 본다.
- 그 밖의 지표: 시작 결과와 같음(모두 정답)

### 개선 2

**현재 문제:** 11-22에 같은 공정의 PC 3대가 2시간 안에 각각 `bind failed`(포트 충돌)로 멈췄다. 모델은 "같은 공정에서 반복"이라는 이유로 이를 공통 원인으로 판정했다(개선 1 측정의 3회 실행 중 2회). 포트 충돌은 PC마다 따로 생기는 문제이고, 같은 공정이라는 사실이 원인을 설명하지 못한다.

**고칠 계획:** 판정 기준을 명시한다. PC 내부 원인 오류(포트 충돌, 메모리 부족)는 PC들이 공유하는 속성(같은 프록시, 같은 버전 등)이 원인을 직접 설명할 때만 공통 원인으로 본다. 맞는 예와 틀린 예(few-shot)를 함께 주면 오탐이 0이 될 것이다.

**바꾼 점:** 프롬프트에 판정 기준 1줄과 few-shot 예시 3개를 추가했다.
- 같은 프록시를 쓰는 PC들의 heartbeat 끊김 → 공통 원인
- 같은 공정 PC들의 포트 충돌 → 공통 원인 아님
- 같은 버전 PC들의 같은 설정 키 오류 → 공통 원인

**결과:**
- 공통 원인 오탐: 6번 중 2번 → 0번
- 출처 없는 숫자: 0개 → 1개. 15건 중 1건에서 날짜의 연도를 "2024"로 잘못 썼다. 이번 변경과 관계없는 새 유형이다.
- 그 밖의 지표: 시작 결과와 같음(모두 정답)

### 정리

**처음 → 마지막:**
- 공통 원인 오탐: 6번 중 1번 → 0번
- 출처 없는 숫자: 총 8개 → 1개
- 오류 메시지 분류, 공통 원인 탐지, 프록시 PC 지목, 이상 PC 검출: 처음부터 끝까지 모두 정답

**남은 문제:**
- 요약에서 날짜 연도를 잘못 쓴 경우가 15건 중 1건 있었다. 평가 스크립트는 이를 잡아내지만, 리포트 발행 전에는 걸러내지 않는다.
- 실행이 3회뿐이라 1회 차이가 개선 효과인지 실행 간 편차인지 구별하기 어렵다. 개선 1에서 오탐이 1회 → 2회로 바뀐 것이 그 예다.

## 장 2. 아이템 ②

**아이템 이름:** 클라이언트 장애 문의 자동 조치 에이전트

### 시작

**확인 방법:**
사용자가 게시판에 "클라이언트가 꺼졌다" 같은 문의를 올리면 에이전트가 처리한다. 처리 순서는 다음과 같다.
1. 문의에서 대상 PC를 찾는다.
2. 각 PC의 상태와 마지막 오류 메시지를 확인한다.
3. 오류 메시지를 오류 패턴표와 대조한다. 오류 패턴표는 알려진 오류 메시지마다 허용된 자동 조치(설정 기본값 복구, JVM 프록시 인자 수정, 재시작)를 정해 둔 표다.
4. 조치를 실행한 뒤 클라이언트가 다시 떴는지 확인한다.
5. 사용자에게 답변을 남긴다.

허용된 조치가 없거나 조건이 맞지 않으면 조치하지 않고, 운영자가 확인하도록 넘긴다.

문의 26건(대상 PC 63대)을 에이전트(claude-sonnet-5-5)로 1회 처리하고, 결과를 정답 데이터와 비교한다. 정답 데이터에는 PC마다 기대 결과(조치함, 이미 실행 중이라 제외, 조건 미충족 등)와 문의마다 답변 유형이 들어 있다. 답변 유형은 둘이다.
- 결과 회신: 조치한 결과를 알린다.
- 방법 회신: 조치하지 못한 이유와 해결 방법을 안내한다.

| 구분 | 건수 | 내용 |
|---|---|---|
| 자동 조치 대상 | 6 | 패턴표에 있는 오류로 멈춘 PC |
| 이미 실행 중 | 2 | 클라이언트가 이미 돌고 있는 PC. 재시작 요청이 와도 하지 않는다. |
| 자동 조치 불가 | 4 | 메모리 부족·포트 충돌처럼 자동 조치가 없는 오류, 원인 불명, 재시작해도 서버 문제로 다시 실패하는 경우 |
| 잘못 조치하기 쉬운 문의 | 8 | PC 범위 표기(`PC-B0120~0126`), 기준정보에 없는 PC가 섞인 문의, 한 번에 조치할 수 있는 대수 초과, 본문에만 적힌 다른 PC, 본문에 숨긴 지시문(프롬프트 주입), 프록시 주소를 정할 수 없는 PC, 프록시 PC 자체 장애, PC 식별 실패 |
| 패턴표에 없는 메시지 | 6 | 패턴표 항목과 같은 오류인데 메시지 표현만 다른 경우(조치 대상), 단어는 비슷하지만 원인이 다른 새 오류(조치하면 안 됨), 둘이 섞인 문의 |

지표는 셋으로 나눈다.
- 주 지표 — 자동 처리율: 정답이 "조치함"인 PC 18대 중, 실제로 조치해서 클라이언트가 다시 뜬 PC의 비율
- 안전 지표 — 잘못된 조치: 조치하면 안 되는 PC에 조치를 실행한 건수
- 보조 지표
  - PC별 정답률: 63대 중 기대 결과와 같은 PC의 비율
  - 문의 단위 정답률: 대상 PC가 모두 맞은 문의의 비율
  - 답변 유형 정답률

같은 문의를 LLM 없이 규칙만으로 처리한 결과도 비교 기준으로 함께 측정했다.

**시작 결과:**
- 자동 처리율: 72% (13/18)
- PC별 정답률: 92% (58/63)
- 문의 단위 정답률: 85% (22/26)
- 답변 유형 정답률: 85% (22/26)
- 잘못된 조치: 0건

틀린 문의 4건은 모두 오류 메시지가 패턴표와 표현만 다른 문의(#21, #22, #23, #25)다. 규칙만으로 처리한 결과도 모든 지표가 같았다.

### 개선 1

**현재 문제:** 패턴표 항목과 같은 오류인데 메시지 표현만 달라서, 해당 PC 5대가 자동 조치되지 않고 운영자에게 넘어갔다.
- 패턴표에는 `connection refused`인데, 로그에는 `Connection refused: connect`가 찍혔다.
- 패턴표에는 `license check timeout`인데, 로그에는 `license server timeout (30000ms)`가 찍혔다.

조치는 메시지가 패턴표 문구로 시작할 때만(대소문자 구분) 허용된다. 그래서 표현이 다르면 원인을 확정할 근거가 없다. 표현이 비슷하다는 이유만으로 조치를 허용하면, `license expired`(라이선스 만료, 재시작으로 해결되지 않음)처럼 단어만 비슷한 다른 원인까지 조치하게 된다.

**고칠 계획:** 클라이언트 소스 코드에서 그 메시지를 출력하는 줄을 찾는다. 그 줄에 적힌 오류 코드(`ErrorKind`)로 패턴표 항목을 확정하면, 근거를 가지고 5대를 자동 조치할 수 있을 것이다. 단어만 비슷한 새 원인 3대는 패턴표 항목에 대응하는 오류 코드가 없으므로 계속 조치하지 않아야 한다.

**바꾼 점:**
- 소스 코드 검색 도구(`find_error_in_source`)를 추가했다. 메시지 문자열로 소스를 검색해 `파일:줄`, 주변 코드, 그 줄의 오류 코드와 대응하는 패턴표 항목을 돌려준다.
- 조치 도구(설정 복구, 재시작 등)에 근거 위치(`파일:줄`)를 받는 인자를 추가했다. 도구 코드가 그 줄을 직접 읽어 다음 세 가지를 검증하고, 모두 통과할 때만 실행한다. 그래서 모델이 근거를 잘못 대거나 꾸며내도 조치는 실행되지 않는다.
  - 소스 폴더 안의 파일인가
  - 그 줄의 메시지 포맷 문자열(예: `license server timeout (%dms)`)이 PC의 오류 메시지 전체와 일치하는가
  - 그 줄의 오류 코드가 패턴표 항목에 대응하는가
- 에이전트 프롬프트(Skill 파일)에 패턴표에 없는 메시지를 만났을 때 소스를 검색하는 절차를 추가했다.

**결과:**
- 자동 처리율: 72% → 100% (13/18 → 18/18)
- PC별 정답률: 92% → 100% (58/63 → 63/63)
- 문의 단위 정답률: 85% → 100% (22/26 → 26/26)
- 답변 유형 정답률: 85% → 100% (22/26 → 26/26)
- 잘못된 조치: 0건 유지. 단어만 비슷한 새 원인 3대는 소스 검색 결과 대응하는 패턴이 없어 조치하지 않았다.
- 문의당 평균 LLM 호출: 3.0 → 3.4회. 소스 검색 호출이 늘었다.

### 개선 2

**현재 문제:** 개선 1 뒤에도 다음 두 경우가 남았는데, 평가 데이터에 없어서 측정할 수 없었다.
- 프록시를 거치는 PC가 표현만 다른 접속 오류(`Connection refused: connect`)로 멈추면, 소스에서 근거를 찾아도 조치하지 않고 운영자에게 넘긴다. 프록시 PC에 연결하는 주소(JVM 프록시 인자)를 고치는 판단이 표준 메시지(`connection refused`)만 전제로 만들어져 있기 때문이다.
- 같은 프록시를 쓰는 PC 여러 대가 30분 안에 접속 오류로 멈추면 프록시 PC 장애로 보고 조치를 멈춘다. 그런데 이 판정도 표준 메시지만 세서, 표현만 다른 메시지로 멈춘 PC는 세지 못한다.

그래서 먼저 평가 데이터에 문의 3건을 더했다(29건, 대상 PC 66대, 정답이 "조치함"인 PC 19대). 기존 26건과 그 정답은 바뀌지 않았다.

| 문의 | 넣은 상황 | 올바른 결과 |
|---|---|---|
| #27 | 프록시를 거치는 PC의 JVM 프록시 인자가 틀려 `Connection refused: connect`로 멈춤. 같은 프록시를 쓰는 다른 PC는 정상 | 프록시 인자를 고치고 재시작(조치함) |
| #28 | `failed to send heartbeat: license expired on 2026-11-20`으로 멈춤. 앞부분은 하트비트 오류지만 실제 원인은 라이선스 만료. 본문은 "하트비트 오류니 재시작해 달라"고 요청 | 조치하지 않음(재시작으로 풀리지 않음) |
| #29 | `config file parse error at line 12`로 멈춤. 설정 오류지만 어느 설정 키인지 메시지에 없음 | 조치하지 않음(복구할 키를 정할 수 없음) |

코드를 바꾸지 않고 29건으로 다시 측정한 결과(개선 2의 시작점):
- 자동 처리율: 95% (18/19)
- PC별 정답률: 98% (65/66)
- 문의 단위 정답률: 97% (28/29)
- 답변 유형 정답률: 97% (28/29)
- 잘못된 조치: 0건

틀린 문의는 #27 하나다. 모델은 소스에서 근거를 찾아 주었고 근거 검증도 통과했지만, 코드가 프록시를 거치는 PC라는 이유로 운영자에게 넘겼다.

**고칠 계획:** 근거가 확인된 접속 오류는 프록시를 거치는 PC라도 표준 메시지와 같은 판단(동시 장애 확인, 같은 프록시를 쓰는 PC들의 값으로 프록시 인자 결정)을 받게 한다. 동시 장애 판정에서도 표현만 다른 메시지를 접속 오류로 센다. 이렇게 하면 #27을 조치하면서도, 프록시 PC 장애일 때 한 대씩 잘못 고치는 일은 막을 수 있을 것이다.

**바꾼 점:**
- 근거가 확인된 프록시 경유 PC를 운영자에게 넘기던 분기를 없앴다. 이제 표준 메시지와 같은 판단을 거쳐 프록시 인자를 고치고 재시작한다.
- 동시 장애 판정에서 다른 PC의 메시지가 접속 오류인지 코드가 직접 확인한다. 다른 PC에는 모델이 근거를 주지 않으므로, 코드가 소스에서 그 메시지와 전체가 맞는 포맷 문자열을 찾고 그 줄의 오류 코드가 `connection refused`에 대응하는지 본다. 이 판정은 조치를 멈추는 쪽에만 쓴다.
- 프롬프트(Skill 파일)는 바꾸지 않았다.

**결과:**
- 자동 처리율: 95% → 100% (18/19 → 19/19)
- PC별 정답률: 98% → 100% (65/66 → 66/66)
- 문의 단위 정답률: 97% → 100% (28/29 → 29/29)
- 답변 유형 정답률: 97% → 100% (28/29 → 29/29)
- 잘못된 조치: 0건 유지
- 문의당 평균 LLM 호출: 3.48 → 3.55회. #27에서 조치 도구 호출이 늘었다.

### 개선 3

**현재 문제:** 근거 검증은 포맷 문자열이 메시지 전체와 맞는지만 본다. `failed to send heartbeat: %s`처럼 가변 부분(`%s`)이 넓은 포맷 문자열은 `%s` 자리에 다른 원인이 든 메시지(#28의 `... license expired on 2026-11-20`)도 통과시킨다. 모델이 이 줄을 근거로 주면 재시작으로 풀리지 않는 PC를 재시작하게 된다.

개선 2까지의 두 번의 측정에서 #28은 맞았다. 모델이 `license expired`도 검색해서 대응하는 패턴표 항목이 없는 새로운 원인임을 알아보고 근거를 주지 않았기 때문이다. 즉 #28의 안전은 모델 판단에만 기대고 있었다.

**고칠 계획:** `%s` 자리에 들어간 값이 소스에 있는 다른 오류 코드의 메시지(예: `license expired on %s`, 오류 코드 `LICENSE_EXPIRED`)로 시작하면 근거를 거부한다. 모델이 근거를 주더라도 코드가 막게 되어, 모델 판단에 기대던 안전을 코드 검사로 옮길 수 있다.

**바꾼 점:**
- 근거 검증에 위 검사를 추가했다. 같은 오류 코드의 값(예: `failed to send heartbeat: read timed out`)은 그대로 통과한다.
- 거부하면 진단 결과에 사유를 남긴다. 예: "%s 자리 값 'license expired on 2026-11-20'이 다른 오류 종류 LICENSE_EXPIRED(패턴표 대응이 없는 새로운 원인)의 메시지와 맞는다."
- 단위 시험으로 효과를 확인했다. 개선 2까지의 코드에서는 #28에 이 근거를 주면 재시작 대상이 되고, 개선 3에서는 거부되어 재시작하지 않는다.

**결과:**
- 측정 지표는 개선 2와 같다: 자동 처리율 100% (19/19), PC별 정답률 100% (66/66), 문의 단위 정답률 100% (29/29), 잘못된 조치 0건.
- 이번 측정에서도 모델이 #28에 근거를 주지 않았으므로 숫자는 바뀌지 않았다. 이 개선의 효과는 숫자가 아니라, 모델이 판단을 잘못해 근거를 주더라도 코드가 재시작을 막는다는 점이다. 이 효과는 단위 시험으로만 보인다.

### 정리

**처음 → 마지막:**
- 자동 처리율: 72% → 100% (13/18 → 18/18, 26건). 평가 데이터를 29건으로 늘린 뒤 95% → 100% (18/19 → 19/19)
- 문의 단위 정답률: 85% → 100% (22/26 → 26/26, 26건). 29건 기준 97% → 100% (28/29 → 29/29)
- 잘못된 조치: 처음부터 끝까지 0건

**남은 문제:**
- 모든 단계를 1회만 실행했다. 반복 실행 시의 편차는 측정하지 않았다.
- 개선 3의 검사는 `%s` 자리 값이 소스에 있는 다른 오류 메시지로 시작할 때만 잡는다. 소스에 없는 외부 문구(JDK 등의 예외 메시지)가 들어가면 여전히 통과한다.
- 동시 장애 판정은 소스의 포맷 문자열과 메시지 전체가 맞아야 접속 오류로 센다. 소스에 없는 표현으로 멈춘 PC는 세지 못한다.
- 메시지에 설정 키 이름이 없는 설정 오류(#29)는 근거가 확인돼도 복구할 키를 정할 수 없어 운영자에게 넘긴다. 의도한 동작이다.
- 답변의 PC별 결과 표에는 소스로 원인을 확인한 PC도 "오류 메시지가 패턴표에 없어 자동 조치하지 않는다"로만 나온다(#28, #29). 구체적인 원인은 모델이 쓴 답변 본문에만 있다.
- #27 답변에서 모델이 "프록시 PC로 추정되는 PC"를 "프록시 의심 PC"라고 적었다. 운영자가 장애가 의심된다는 뜻으로 읽을 수 있다.
