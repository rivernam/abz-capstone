# 구현 명세 (14시 이후 결정)

`ABZ_과제정의서.docx`는 2026-11-26 14시 기준으로 고정한다. 이 문서는 그 이후 대화에서 정한, 실제 구현을 위한 결정을 모은 것이다. 정의서와 다른 부분은 이 문서가 구현의 기준이다.

## 1. 정의서에 반영하지 않은 변경

- 아이템 ②는 대상 PC가 한 대가 아니라 목록일 수 있다(범위, 쉼표 목록).
- 서버 실행 로그는 어제와 오늘 두 날짜가 아니라 3일치(전일 대비 계산용)를 읽는다.
- 쓰기 Tool은 `pc_id`가 아니라 `post_id`를 받는다.
- 정의서의 함정 목록에 추가될 항목: 대상이 범위로 적힌 문의, 범위 안에 미등록 PC가 섞인 문의, 자동 조치 상한을 넘는 범위.

## 2. 실행 구조

- 사내 서버에서는 우리 코드가 LLM API를 직접 호출한다. 키는 환경변수(`ANTHROPIC_API_KEY`)로 읽고 코드와 제출 파일에 넣지 않는다.
- `tools/*.py`와 `.claude/skills/*/SKILL.md`를 Claude Code와 서버 러너가 공통으로 쓴다. 서버 러너는 Skill 본문과 CLAUDE.md를 시스템 프롬프트로 읽는다.
- 아이템 ①은 고정 파이프라인이다. 스케줄러가 순서대로 코드를 돌리고, LLM은 원인 후보 정리와 리포트 문장 작성에만 쓴다.
- 아이템 ②는 수동 에이전트 루프다(호출 상한, 로깅을 직접 건다). 읽기 Tool은 자유롭게 고르고, 쓰기 Tool은 Tool 코드 안의 조건 검사를 통과해야 실행된다.
- Hook은 서버에서 동작하지 않으므로 안전 검사는 Tool 코드 안에 둔다(ADR 0001).

## 3. Tool 설계 원칙

- 쓰기 Tool(`update_client_config`, `restart_client_service`, `publish_report`, `post_operator_note`)에는 멱등 키를 둔다. 같은 호출이 재시도되어도 중복 발송이나 중복 조치가 일어나지 않게 한다.
- 조치 대상 PC는 모델이 정하지 않는다. 쓰기 Tool은 `post_id`를 받고, 대상은 서버가 게시글 레코드에서 읽는다.
- Tool 설명은 "무엇을 하는지, 언제 쓰고 언제 쓰지 않는지, 인자, 한계"를 3~4문장 이상 쓴다.
- 오류는 예외로 끝내지 않고 `is_error` 결과로 돌려준다. 무엇이 틀렸고 다음에 무엇을 할지를 적는다. 결과 크기는 제한한다.
- 게시글 본문은 사용자가 쓴 자유 텍스트이므로 신뢰하지 않는다.

## 4. 가상 세계 (구현 완료분)

- 위치: `abz-capstone/`. 생성기 `generator/make_world.py`는 시드 고정이라 같은 결과가 나온다.
- 기준정보 DB: 가상 PC 300대(공정 5개 × 60대), 테이블 `pc_master`.
- 서버 실행 로그: `재료/서버로그/server_YYYY-MM-DD.txt`, 11-24 ~ 11-26(오전 8시까지). 한 줄은 `시각 | PC ID | 이벤트 | 버전 | 설비 PC IP [| 오류 메시지]`. 이벤트는 HEARTBEAT(10분 간격), START, STOP, ERROR.
- 정답표: `기록/정답표_일일리포트.json`. 생성기가 심은 시나리오를 그대로 기록하므로 채점이 자동이다.

### 이상 PC 판정 기준 (리포트 날짜 기준)

- 정상 신호 간격이 30분 이상이면 `heartbeat_gap`이다. 간격은 앞쪽 정상 신호가 속한 날짜로 귀속시킨다.
- 하루에 START 이벤트가 5회 이상이면 `restart_loop`이다.
- ERROR 이벤트가 하나라도 있으면 `error`이다.
- DB에 있는 PC인데 그 날짜 로그가 한 줄도 없으면 `no_report`이다. 서버 로그만으로는 "실행 안 됨"과 "로그 누락"을 구분할 수 없으므로 "확인 필요"로 표시한다.
- DB에 없는 PC의 로그는 이상 PC 통계에 넣지 않고 미등록으로 따로 보고한다.
- 로그의 IP가 DB의 IP와 다르면 기준정보 오입력 의심으로 따로 표시한다.
- 정상이어야 하는 함정: 자정 전후 계획된 재시작(정상 신호 간격 약 20분). 이상으로 잡으면 오류다.

## 5. 아이템 ② 조치 규칙

### 대상 해석

- 조치 대상은 코드 파서가 게시글의 설비 PC ID 필드에서만 만든다. 지원 표기는 `PC-A0101~0110`, `PC-A0101~PC-A0110`, 쉼표 목록이다.
- 본문(증상 설명)에 언급된 PC는 조치 대상이 아니다. 회신에 "필드에 없어 제외했다"고만 알린다.
- 한 문의에서 자동 조치하는 대수는 20대로 제한한다. 상한을 넘으면 앞에서부터 20대까지만 조치하고, 조치하지 못한 PC는 회신에 안내한다.

### PC별 독립 처리

- 조치 조건: 기준정보에 있는 PC, 서비스 상태가 정지, 허용 목록의 설정 키, 허용 범위 안의 값.
- 조건을 충족하지 못하는 PC는 조치하지 않고 사유를 기록한다.
- 설정 수정 전에 백업하고, 재시작 후 클라이언트 로그와 상태로 검증한다. 실패하면 그 PC만 원복한다. 성공한 PC의 조치는 유지한다.
- 회신 초안에는 PC별 결과(조치함, 이미 실행 중이라 제외, 조건 미충족, 실패 후 원복, 상한 초과)를 표로 적는다.

### 회신

- 조치를 실행했으면 결과 회신, 실행하지 않았으면 방법 회신이다. 둘 다 초안이다.
- 초안과 조치 이력은 해당 게시글의 운영자 전용 메모로만 등록한다. 공개 범위는 코드에서 고정한다. 이유는 검토 전 초안이 사용자에게 보이면 안 되기 때문이다(IP는 비공개 정보가 아니다).

## 6. 개선 과정 계획

- ①의 1차 개선안은 시작 결과를 측정한 뒤 정한다.
- ②의 1차 개선은 소스 검색(`find_error_in_source`, 문자열 검색) 추가다. 처음 버전은 오류 메시지 패턴표로 판단한다. 개선 단계용 가상 Java 소스는 그때 만든다.

## 7. 구현 순서

1. 공통 기반: 가상 DB, 생성기, `get_pc_info` (완료, 테스트 통과).
2. 아이템 ① 끝까지 한 번 돌리기: `summarize_daily_logs`, `publish_report`, `daily-report` Skill, 가상 object storage와 outbox.
3. 가상 게시판: SQLite, 명령줄 도구, 정적 HTML 화면. 문의 등록, 조회, 운영자 전용 메모.
4. 아이템 ② 끝까지 한 번 돌리기: 가상 PC 폴더(클라이언트 로그, 설정, java 실행 인자, 서비스 상태), 나머지 Tool, 대상 파서, Skill 2개, 에이전트 루프.
5. 시험 세트와 시작 결과 측정: 문의 20건과 정답, 리포트 정답표로 채점.
6. 제출 패키징: 코드 ZIP과 작업 폴더 ZIP, API 키 검사.
