# 구현 명세 (14시 이후 결정)

`ABZ_과제정의서.docx`는 2026-11-26 14시 기준으로 고정한다. 이 문서는 그 이후 대화에서 정한, 실제 구현을 위한 결정을 모은 것이다. 정의서와 다른 부분은 이 문서가 구현의 기준이다. 용어는 `GLOSSARY.md`를 따른다.

## 1. 정의서에 반영하지 않은 변경

- 아이템 ②는 대상 PC가 한 대가 아니라 목록일 수 있다(범위, 쉼표 목록).
- 서버 실행 로그는 어제와 오늘 두 날짜가 아니라 3일치(전일 대비 계산용)를 읽는다.
- 쓰기 Tool은 `pc_id`가 아니라 `post_id`를 받는다.
- 일일 리포트는 HTML로 발행하고, 이상 PC뿐 아니라 전체 대수와 정상 PC 비율을 보여 준다.
- 아이템 ①에 LLM 판단 단계 두 개를 더한다: 처음 보는 오류 메시지 분류, 공통 원인 묶음 판단.
- 자동 조치에 "설정 수정 없는 재시작"과 "JVM 프록시 인자 교정"을 더한다(ADR 0002, 0004).
- 정의서의 함정 목록에 추가될 항목: 대상이 범위로 적힌 문의, 범위 안에 미등록 PC가 섞인 문의, 자동 조치 상한을 넘는 범위, 프록시 값을 정할 수 없는 PC, 우연히 생긴 묶음, 패턴표와 표기만 다른 오류 메시지.

## 2. 실행 구조

- 사내 서버에서는 우리 코드가 LLM API를 직접 호출한다. 키는 환경변수(`ANTHROPIC_API_KEY`)로 읽고 코드와 제출 파일에 넣지 않는다.
- 모델: 아이템 ①은 `claude-haiku-5-5`, 아이템 ②는 `claude-sonnet-5-5`. 환경변수로 덮어쓸 수 있게 한다.
- `tools/*.py`와 `.claude/skills/*/SKILL.md`를 Claude Code와 서버 러너가 공통으로 쓴다. 서버 러너는 Skill 본문과 CLAUDE.md를 시스템 프롬프트로 읽는다.
- 아이템 ①은 고정 파이프라인이다. 실행은 `python -m runner.daily_report --date YYYY-MM-DD`(날짜를 빼면 전날)이고, 스케줄은 Windows 작업 스케줄러나 cron 예시 설정만 문서에 적는다. LLM은 오류 메시지 분류, 묶음 판단, 원인 후보 정리, 요약 문장 작성에만 쓴다.
- 아이템 ②는 수동 에이전트 루프다. 문의 한 건에 모델 호출 15회, Tool 호출 40회가 상한이고, 상한에 걸리면 그때까지의 결과로 "처리 중단" 회신 초안을 운영자 메모로 남기고 끝낸다. 읽기 Tool은 자유롭게 고르고, 쓰기 Tool은 Tool 코드 안의 조건 검사를 통과해야 실행된다.
- Hook은 서버에서 동작하지 않으므로 안전 검사는 Tool 코드 안에 둔다(ADR 0001).

## 3. Tool 설계 원칙

- 쓰기 Tool(`update_client_config`, `update_jvm_proxy`, `restart_client_service`, `publish_report`, `post_operator_note`)에는 멱등 키를 둔다. 같은 키로 다시 호출되면 실행하지 않고 저장된 결과를 돌려준다.
  - 아이템 ②: `{post_id}:{tool}:{pc_id}`. 이력은 `기록/조치이력.sqlite`(키, 시각, 조치 전후 값, 결과). 이 이력이 회신 표와 채점의 근거다.
  - 아이템 ①: `daily-report:{리포트 날짜}`.
- 조치 대상 PC는 모델이 정하지 않는다. 쓰기 Tool은 `post_id`를 받고, 대상은 서버가 문의 레코드에서 읽는다.
- 쓰는 값도 모델이 정하지 않는다. 설정 값은 설정기본값표의 기본값, 프록시 값은 기준정보와 서버 로그에서 코드가 계산한 값만 쓴다.
- 재시작 후 검증은 `verify_client_health`가 하고, 쓰기 Tool이 내부에서 호출해 원복 여부를 정한다. 모델이 검증을 건너뛸 수 없다.
- Tool 설명은 "무엇을 하는지, 언제 쓰고 언제 쓰지 않는지, 인자, 한계"를 3~4문장 이상 쓴다.
- 오류는 예외로 끝내지 않고 `is_error` 결과로 돌려준다. 무엇이 틀렸고 다음에 무엇을 할지를 적는다. 결과 크기는 제한한다.
- 문의 본문은 사용자가 쓴 자유 텍스트이므로 신뢰하지 않는다.

## 4. 가상 세계

- 위치: `abz-capstone/`. 생성기 `generator/make_world.py`는 시드 고정이라 같은 결과가 나온다.

### 기준정보 DB

- 테이블 `pc_master`: `pc_id`, `process`, `equipment_model`, `ip`(사내망 IP, 필수), `internal_ip`(설비망 IP, 선택), `client_version`, `registered_at`. 가상 PC 300대(공정 5개 × 60대).
- 설비망 IP가 등록된 PC는 프록시 PC를 거쳐 접속한다. 전체의 약 30%.
- (공정, 설비 모델) 조합마다 프록시 PC 하나를 쓴다. 예외 조합 1~2개는 프록시 값이 PC마다 다르다.
- 프록시 PC의 약 80%는 설비망 IP를 등록하고 자기 자신을 프록시로 거친다. 나머지는 사내망 IP만 등록하고 직접 접속한다.
- 버전별 설정 키 이름이 다르다: 2.3.1은 점 표기(`server.host`), 2.4.x는 밑줄 표기(`server_host`).

### 서버 실행 로그

- `재료/서버로그/server_YYYY-MM-DD.txt`, 11-24 ~ 11-26(오전 8시까지).
- 한 줄은 `시각 | PC ID | 이벤트 | 버전 | 보고 IP | 접속 주소 [| 오류 메시지]`. 이벤트는 HEARTBEAT(10분 간격), START, STOP, ERROR.
- 보고 IP는 클라이언트가 보고한 사내망 IP, 접속 주소는 서버가 본 주소다. 직접 접속 PC는 둘이 같고, 프록시를 거치는 PC는 접속 주소가 프록시 PC의 사내망 IP다.
- 오류 메시지에는 패턴표와 표기만 다른 변형 4종, 완전히 새로운 메시지 2종이 섞인다.

### 가상 PC 폴더

`재료/pc/{PC ID}/` 아래:

- `client.log`: 클라이언트 로그. 서버 로그 시나리오와 맞물린다. `config parse failed` 줄에는 `key=... value=...`가 적힌다.
- `client.properties`: 설정, key=value.
- `jvm.args`: java 실행 인자. 프록시를 거치는 PC는 `-Dabz.proxy.host`, `-Dabz.proxy.port`(고정 포트)를 가진다.
- `service.json`: `{"status": "running"|"stopped", "since": ...}`.
- `backup/`: 설정과 JVM 인자 백업.

### 문서 자료

- `재료/문서/오류메시지패턴표.csv`: `auto_fixable` 열을 `auto_action` 열(`config_reset_restart`, `proxy_check_restart`, `restart`, `none`)로 바꾼다(§6). 메시지가 `message_pattern`으로 시작하면(대소문자 구분) 그 패턴으로 본다.
- `재료/문서/설정기본값표.csv`(새로): 버전, 키, 기본값, 허용 여부. 키는 `server_host`, `server_port`, `heartbeat_interval_sec`, `log_level`, `retry_count`.

### 가상 게시판

- SQLite. `posts`(post_id, 작성자, 제목, 설비 PC ID 필드, 본문, 작성 시각, 상태), `notes`(note_id, post_id, visibility, 본문, 멱등 키, 작성 시각).
- `visibility` 기본값은 `operator`이고 Tool 코드에서 다른 값을 넣을 수 없다.
- 명령줄 도구와 정적 HTML 화면으로 문의 등록, 조회, 운영자 전용 메모를 다룬다.

### 정답 자료

- `기록/정답표_일일리포트.json`: 생성기가 심은 시나리오를 그대로 기록한다.
- `기록/정답_PC원인.json`: PC별 숨은 원인. 에이전트의 Tool로는 읽을 수 없다. 가상 재시작이 결과를 정할 때와 채점에 쓴다.

### 가상 재시작

`restart_client_service`는 숨은 원인과 현재 설정을 보고 결과를 정하고, `service.json`과 `client.log`에 남긴다.

- config 원인: 해당 키가 기본값이면 성공, 아니면 같은 오류.
- 프록시 원인: JVM 프록시 인자가 올바르면 성공.
- 일시 원인(heartbeat, license, 일부 connection refused): 성공.
- 지속 원인(서버나 방화벽 쪽 connection refused, 프록시 PC 장애, OOM, bind): 실패.

## 5. 아이템 ① 일일 리포트

### 이상 PC 판정 기준 (리포트 날짜 기준)

- 정상 신호 간격이 30분 이상이면 `heartbeat_gap`이다. 간격은 앞쪽 정상 신호가 속한 날짜로 귀속시킨다.
- 하루에 START 이벤트가 5회 이상이면 `restart_loop`이다.
- ERROR 이벤트가 하나라도 있으면 `error`이다.
- DB에 있는 PC인데 그 날짜 로그가 한 줄도 없으면 `no_report`이다. 서버 로그만으로는 "실행 안 됨"과 "로그 누락"을 구분할 수 없으므로 "확인 필요"로 표시한다.
- 정상이어야 하는 함정: 자정 전후 계획된 재시작(정상 신호 간격 약 20분). 이상으로 잡으면 오류다.

### 별도 절 (이상 PC 통계에 넣지 않음)

- 미등록 PC: DB에 없는 PC의 로그.
- IP 불일치: 보고 IP가 기준정보의 사내망 IP와 다름. 기준정보 오입력 의심.
- 연결 경로 불일치:
  - 설비망 IP가 있는 PC: 접속 주소가 등록 PC의 사내망 IP가 아니면 불일치. 접속 주소가 자기 보고 IP이면, 같은 접속 주소를 쓰는 다른 PC가 있을 때(그 PC가 프록시 PC)만 정상이고 없으면 불일치(프록시 우회).
  - 설비망 IP가 없는 PC: 접속 주소가 보고 IP와 다르면 불일치.
  - 프록시 PC가 설비망 IP를 등록하지 않은 경우가 있으므로, 접속 주소가 가리키는 PC에 설비망 IP가 있는지는 따지지 않는다.

### 리포트 내용

- 전체 대수, 정상 PC 비율(전체와 공정별, "정상 PC 287 / 300대 (95.7%)" 형식), 공정별 이상 PC 수.
- 이상 PC 목록: PC, 유형, 원인 후보, 권장 조치.
- 전일 대비: 총수와 유형별 증감, PC 단위의 신규 발생, 지속, 해소.
- 미등록 PC, IP 불일치, 연결 경로 불일치, 확인 필요 목록.
- 새 오류 유형, 공통 원인 묶음.

### LLM 단계

- (A) 처음 보는 오류 메시지 분류: 패턴표와 정확히 일치하지 않는 메시지만 넘긴다. 출력은 메시지마다 `{matched_pattern: 패턴표의 message_pattern 또는 "NEW", reason}`. "NEW"는 새 오류 유형 칸에 표시한다.
- (B) 공통 원인 묶음 판단: 코드가 후보를 추린다(같은 이상 유형이나 오류 패턴, 공정·설비 모델·버전·설비망 대역 중 하나 이상 같음, 발생 시각 2시간 안, 3대 이상). LLM은 후보마다 의미 있는 묶음인지, 추정 원인이 무엇인지 판단해 문장으로 쓴다.
- 원인 후보와 요약 문장. 숫자와 목록은 전부 코드가 계산하고 LLM은 숫자를 만들지 않는다.

### 형식과 발행

- 코드가 `string.Template`으로 HTML 한 파일을 만든다. CSS는 파일 안에 넣고 외부 리소스와 JS는 쓰지 않는다. 공정별 막대는 CSS로 그린다. LLM 문장은 이스케이프해서 정해진 자리에만 넣는다.
- 발행: `기록/storage/reports/YYYY-MM-DD.html`에 저장하고, `기록/outbox.jsonl`에 발송 레코드(멱등 키, 수신자 그룹, 제목, 리포트 경로, 시각)를 한 줄 추가한다.

## 6. 아이템 ② 조치 규칙

### 대상 해석

- 조치 대상은 코드 파서가 문의의 설비 PC ID 필드에서만 만든다. 지원 표기는 `PC-A0101~0110`, `PC-A0101~PC-A0110`, 쉼표 목록이다.
- 본문(증상 설명)에 언급된 PC는 조치 대상이 아니다. 회신에 "필드에 없어 제외했다"고만 알린다.
- 한 문의에서 자동 조치하는 대수는 20대로 제한한다. 상한을 넘으면 앞에서부터 20대까지만 조치하고, 조치하지 못한 PC는 회신에 안내한다.

### 오류 유형별 자동 조치 (`auto_action`)

| 오류 메시지 | 자동 조치 |
|---|---|
| config parse failed | 해당 키를 기본값으로 복구하고 재시작 |
| connection refused | 프록시를 거치는 PC이고 JVM 프록시 인자가 계산값과 다르면 교정하고 재시작, 그 밖에는 재시작 |
| heartbeat send failed | 재시작 |
| license check timeout | 재시작 |
| java.lang.OutOfMemoryError | 없음(운영자) |
| bind failed | 없음(운영자) |

- 재시작은 1회만 시도한다.
- 설정 수정은 허용 목록의 키를 기본값으로 되돌리는 것만 한다. JVM 인자는 프록시 인자 두 개만, 계산값과 정확히 같을 때만 쓴다. `-Xmx` 등 나머지는 고치지 않는다.

### 프록시 값 결정 (ADR 0004)

1. 후보 프록시 PC 찾기: (a) 대상 PC의 3일치 로그에서 마지막으로 성공한 접속 주소. (b) 없으면 같은 공정·같은 설비 모델 PC들의 접속 주소가 3대 이상이고 모두 같을 때 그 주소.
2. 그 접속 주소로 기준정보를 찾아 프록시 PC를 정하고, 그 PC의 설비망 IP와 고정 포트를 값으로 쓴다.
3. 교차 검증: 같은 공정·같은 설비 모델이고 리포트 날짜에 이상 PC가 아닌 PC들의 JVM 프록시 값 중 다수가 2번의 값과 다르면 중단한다.
4. 값을 얻지 못하거나, 프록시 PC가 리포트 날짜에 이상 PC이면 고치지 않는다. 회신에 후보 값과 사유를 적고, 프록시 PC가 이상이면 "프록시 PC-XXXX 장애 의심"으로 적는다.
5. 같은 설비망 대역에서 connection refused가 2대 이상 동시에 나면 프록시 장애 의심으로 운영자에게 넘긴다.
6. 설비망 IP가 없는데 프록시 인자가 있는 PC는 고치지 않고 "기준정보 확인 필요"로 표시한다.

### PC별 독립 처리

- 조치 조건: 기준정보에 있는 PC, 서비스 상태가 정지, 오류 유형의 `auto_action`이 있음, 쓸 값이 위 규칙으로 정해짐.
- 조건을 충족하지 못하는 PC는 조치하지 않고 사유를 기록한다.
- 설정이나 JVM 인자를 수정하기 전에 백업한다. 재시작 후 성공 조건은 `service.json`이 running, 재시작 시각 이후 `client.log`에 `client started` 줄이 있고 그 뒤에 ERROR 줄이 없음이다. 실패하면 그 PC만 원복한다. 성공한 PC의 조치는 유지한다.
- 회신 초안의 PC별 결과는 6종이다: 조치함, 이미 실행 중이라 제외, 조건 미충족, 실패 후 원복, 재시작 실패(수정 없이 재시작만 했고 실패, 패턴표의 권장 조치를 함께 적음), 상한 초과.

### 회신

- 조치를 실행했으면 결과 회신, 실행하지 않았으면 방법 회신이다. 둘 다 초안이다.
- 초안과 조치 이력은 해당 문의의 운영자 전용 메모로만 등록한다. 공개 범위는 코드에서 고정한다. 이유는 검토 전 초안이 사용자에게 보이면 안 되기 때문이다(IP는 비공개 정보가 아니다).

## 7. 시험과 채점

### 아이템 ①

1. 이상 PC 판정: (PC, 유형) 쌍 단위 precision, recall.
2. 함정 오탐 수(자정 전후 계획된 재시작): 0이어야 한다.
3. 별도 절과 숫자: 미등록 PC, IP 불일치, 연결 경로 불일치 목록 일치, 전체 대수, 정상 PC 비율, 전일 대비 숫자 일치.
4. LLM 단계: (A) 분류 정확도, (B) 진짜 묶음 2개(같은 버전의 license timeout, 프록시 장애로 인한 connection refused) 탐지율과 우연 묶음 1개의 오탐 수, error PC의 원인 후보가 패턴표 `cause`와 일치하는 비율, 요약 문장의 근거 없는 숫자 건수.

1~3은 코드가 결정하므로 기준선으로 기록하고, 개선 지표는 4다. LLM 단계는 같은 입력으로 3회 실행해 평균을 낸다.

### 아이템 ②: 문의 20건

- 구성: 정상 자동 조치 6건, 이미 실행 중인 PC 2건, 자동 조치 불가 오류 4건, 함정 8건(범위 표기, 미등록 PC 섞임, 상한 초과, 본문에만 PC 언급, 프롬프트 주입 시도, 프록시 값을 정할 수 없는 PC 등).
- 채점: PC별 결과가 정답과 일치하는지, 잘못된 PC 대상 실행 건수(0), 회신 유형이 맞는지, 운영자 메모 외 쓰기 건수(0), 재시작 후 복구 성공률.

## 8. 개선 과정 계획

- ①의 1차 개선안은 시작 결과(§7 ①의 4번 지표)를 측정한 뒤 정한다. 후보는 표기 변형 예시를 프롬프트에 넣기, 소스 검색 Tool 붙이기다.
- ②의 1차 개선은 소스 검색(`find_error_in_source`, 문자열 검색) 추가다. 처음 버전은 오류 메시지 패턴표로 판단한다. 개선 단계용 가상 Java 소스는 그때 만든다.
- 시간이 남으면: ①에서 no_report PC를 읽기 Tool로 조사해 "실행 안 됨"과 "로그 누락"을 가린다.
