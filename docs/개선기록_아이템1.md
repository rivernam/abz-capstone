# 아이템 ① 개선 기록

시험 세트: 리포트 날짜 5일(2026-11-21~25), 날짜별 함정. 모델 `claude-haiku-5-5`, 같은 입력으로 3회 실행한 평균. 채점: `python -m eval.score_daily_report --runs 3 --label <이름>`.

## 시작 결과 (baseline)

코드가 결정하는 판정(이상 PC precision/recall 1.0, 함정 오탐 0, 식별 실패 사유 정확도 1.0)은 기준선으로 고정된다. LLM 부분에서 두 가지가 틀렸다.

| 지표 | baseline | v1 |
|---|---|---|
| 메시지 분류 정확도 | 1.0 | 1.0 |
| 진짜 묶음 탐지율 | 1.0 | 1.0 |
| 프록시 PC 정확도 | 1.0 | 1.0 |
| 우연 묶음을 묶음으로 판정(회/실행) | 0.33 | 0 |
| 근거 없는 숫자(개/실행) | 2.67 | 0.33 |

- 근거 없는 숫자: 묶음 후보의 PC 수를 모델이 직접 세어 "4대"로 썼다(값은 맞지만 규칙 위반). 오류 메시지의 포트 번호 8443을 요약에 옮겼다.
- 우연 묶음: 11-22 CLEAN 공정의 `bind failed` 3대를 "공정 단위 반복"이라며 묶음으로 판정했다(3회 중 1회).

## 1차 개선 (v1)

- 입력: 묶음 후보마다 PC 수를 코드가 계산해 `facts.cluster_candidate_pc_counts`로 준다.
- Skill: "세어서 숫자를 만들지 않는다", "오류 메시지 속 숫자와 시각은 쓰지 않는다" 규칙 추가. 원인이 PC 안에 있는 오류(포트 충돌, 메모리 부족)는 공유 속성이 원인을 직접 설명할 때만 묶음이라는 기준과 판단 예시 3개 추가.
- 채점 기준(숫자 검사기)은 바꾸지 않았다.

## 남은 문제

v1에서 남은 근거 없는 숫자:

```
2 2026-11-24 ['2024-11-24'] 2024-11-24 기준 정상 PC는 300대 중 291대이며 정상 비율은 97.0%입니다. 이상 PC는 9대로 전일의 33대보다 줄었습니다. 클라이언트 2.4.2 버전에서 설정 파싱 실패 패턴이 4대에 함께 나타나 의미 있는 묶음으로 판단했고, 배포 설정 확인이 우선입니다. 식별 실패가 3건 있어 확인이 필요하며, 확인 필요 PC는 0대입니다.
```
