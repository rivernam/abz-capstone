# 에이전트 구조 해설: 일반 원칙과 이 프로젝트의 선택

AI 활용 에이전트를 만들 때 이 프로젝트의 구조가 일반적인 방식인지 정리한다. 큰 틀은 실무에서 권장하는 설계를 따르고, 일부는 이 과제 상황에 맞춘 선택이다.

## 일반적으로 통하는 부분

| 원칙 | 이 프로젝트에서 | 위치 |
|---|---|---|
| 워크플로와 에이전트를 구분해 쓴다 | 아이템 ①은 순서가 정해진 일이라 코드가 흐름을 쥐고 LLM은 한 번만 판단한다. 아이템 ②는 문의마다 필요한 단계가 달라 LLM이 Tool을 고른다 | `runner/daily_report.py`, `runner/inquiry_agent.py` |
| 에이전트 본체는 단순한 루프다 | 모델 호출 → Tool 실행 → 결과를 다시 전달하는 과정을 끝날 때까지 반복한다 | `runner/inquiry_agent.py` |
| 숫자와 조치 대상은 코드가 정한다 | 집계, PC 수, 조치 대상 PC는 Tool과 러너가 계산하고, LLM은 판단과 문장만 맡는다 | `tools/`, `abzlib/` |
| 안전 검사는 Tool 코드 안에 둔다 | 쓰기 Tool이 대상 PC, 오류 패턴, 설정 허용 목록을 직접 다시 확인한다. 쓰기 전 백업, 재시작 후 검증, 실패 시 원복, 멱등 키가 있다 | `tools/inquiry_tools.py`, [ADR 0001](adr/0001-안전-검사는-Tool-코드-안에-둔다.md) |
| 외부 입력은 데이터로만 다룬다 | 문의 본문을 `<post>`로 감싸고 그 안의 지시를 따르지 않게 한다 | `runner/inquiry_agent.py`, `CLAUDE.md` |
| 호출 상한과 실패 시 대체 경로를 둔다 | 문의 한 건에 모델 15회, Tool 40회가 상한이다. LLM이 실패해도 리포트의 숫자 부분은 발행한다 | `runner/` |
| 정답표로 채점하며 개선한다 | 단계마다 이름을 붙여 같은 시험 세트로 측정한다 | `eval/`, `기록/평가/` |

고정 파이프라인으로 되는 일은 에이전트로 만들지 않는다는 것이 가장 널리 권장되는 기준이다. 프롬프트에 적은 금지 사항은 뚫릴 수 있으므로, 막아야 하는 동작은 코드에서 막는다.

## 이 프로젝트만의 선택

| 선택 | 이유 | 일반적인 경우 |
|---|---|---|
| `CLAUDE.md`와 `SKILL.md`를 서버 러너의 시스템 프롬프트로 같이 쓴다 | 개발할 때와 서버에서 돌 때 같은 규칙을 적용한다 | 프롬프트 파일을 따로 관리한다 |
| 프레임워크 없이 Messages API를 직접 호출한다 | 규모가 작고 동작을 설명해야 하는 과제다 | 규모가 커지면 Agent SDK나 LangGraph 같은 도구를 쓰는 경우가 많다 |
| 사람 승인 없이 자동 조치한다([ADR 0002](adr/0002-설정-수정과-재시작은-승인-없이-자동-실행한다.md)) | 대상이 이미 멈춘 클라이언트라 재시작의 위험이 낮다 | 결제, 삭제, 외부 발송처럼 위험이 큰 작업은 사람 승인 단계를 둔다 |
| RAG를 쓰지 않는다([ADR 0003](adr/0003-RAG-아이템-대신-일반-아이템-2개로-구성한다.md)) | 문의 대응의 핵심이 문서 검색이 아니라 Tool 동작이다 | 문서 기반 질의응답이 핵심이면 RAG를 쓴다 |
| 가상 세계 생성기로 데이터를 만든다 | 실제 데이터가 없는 과제다 | 실제 로그와 과거 문의로 시험 세트를 만든다 |

## 실제 서비스라면 더 붙는 것

이 프로젝트에는 없지만 운영 환경에서는 보통 추가된다.

- 대화 기록과 장기 메모리 저장. 여기는 문의 한 건으로 끝나는 구조다.
- 추적·모니터링 도구와 비용 집계. 여기는 `기록/runs/`의 JSON 실행 기록으로 대신한다.
- 인증과 권한, 동시 실행 처리, 재시도 큐.
- 여러 에이전트로 나누는 구조. 일이 충분히 복잡할 때만 쓴다.
